# 2026-09-17 — live Wasm heap lifetime validation

Hypothesis: the host decoder can reject stale or never-allocated Wasm value pointers without adding imports, a public runtime export, or a new ABI version by publishing the successful invocation's bump-allocator endpoint in the already-reserved low-memory scratch area.

Implementation commit `582989f17816cab6b7bb4afea7fd4ea02d98cf4b` reserves private memory word 12 for the current successful `main` invocation's live heap endpoint. `main` clears the word before execution and writes the final bump cursor only after the source entry returns successfully. A trap therefore cannot leave the previous invocation's lifetime advertised. The host decoder treats static `[16, heap_start)` and dynamic `[heap_start, live_heap_end)` as separate valid regions, rejects values that cross the static/dynamic boundary, and rejects pointers into grown-but-unallocated linear-memory capacity. Older ABI-2 artifacts leave word 12 zero and retain the previous page-bounds decoder behavior. This private watermark is a defensive integrity/lifetime check, not a hostile-module sandbox: a deliberately forged module can write its own memory.

`execute` now reports `metrics.heap_bytes`, the successful invocation's dynamic bump allocation in bytes. A source program returning only pooled static values reports zero. This is allocator use, not peak resident memory and not retained-live-object size.

Local Node 22.16.0 / Linux evidence:

- Exact pre-change production blobs for `src/wasm.mjs` and `src/wasm-host.mjs` were reconstructed from live main and hash-checked byte-for-byte (`3f6bce20fa8478c0468cf95246e47555ad559cea` and `41f72c711f056b46e2148d9a7805c1bbb860d842`) before applying the change. The current runtime helper blob was likewise reconstructed exactly (`2b255df9dc8f48c080f57a1250e52f6e1f644ff6`).
- Targeted exact-current-backend tests: 22/22 passed, covering the four new heap-lifetime cases plus existing Wasm arithmetic/closure/fuel/memory, ABI-integrity, source-location, and embedded-provenance cases.
- Recovered full Wasm handoff with the same lifetime change: `npm test` passed 104/104; `npm run verify` passed those tests, all four examples, README execution, standalone Wasm execution, 500/1,000/2,000 compile work gates and the 1,000-element map/fold engine-stage check.
- `npm run bench -- --sizes 500,1000,2000 --samples 11 --output benchmarks/heap-lifetime-compile.json` passed; `npm run bench:runtime` passed checksum 500500 with 11 samples and 100 calls/sample. These are shared-host observations, not a speed claim.
- Against the exact current backend baseline, the successful-run watermark adds 21 bytes to `return 1;` and 20 bytes to each of arithmetic, array, and map sample artifacts. Wasm function counts and the public export set are unchanged.

Four new adversarial checks cover an aligned pointer into the unused tail of a grown page, an object header straddling the static/dynamic boundary, clearing the watermark across a trapped invocation, and the new dynamic-heap metric. The first two previously passed the host's coarse linear-memory page bound even though they did not identify a value inside the current allocation lifetime.

Limitations: no reclamation or GC was added; values are still invalidated by the next `main` call, and returned closures remain non-callable from the public host ABI. Old ABI-2 artifacts intentionally fall back to the older page-capacity decoder because they do not publish a live heap endpoint. Next allocator work should audit nested/aggregate liveness, host-callable value lifetime, and ownership/GC rather than treating this watermark as memory management.
